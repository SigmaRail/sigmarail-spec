# SigmaRail Spec contributor notes

`sigmarail-spec` is the canonical versioned contract for the SigmaRail Sharadar data model and the current
Studio/LEAN strategy surface. Keep it compact, deterministic, and limited to capabilities that
exist in source code.

## Source ownership and generation

- SQL DDL and `xform_*` views in SigmaRail are authoritative for tables, columns, comments, transforms,
  and Sharadar lineage. Do not hand-edit generated `src/sigmarail_spec/data/lineage.json` or
  `transforms.json`.
- VeraBase, VeraTradingLab, and Studio source contracts are pinned in `spec/sources.lock.json`.
  Generated JSON is refreshed only after reviewing input changes and the lock diff.
- Semantics that cannot be derived from SQL or code belong in `metadata/annotations.json` under
  stable generated IDs, with review and source citations where applicable.
- Keep module ownership and optionality explicit. The module proposal in
  `docs/MODULE_ARCHITECTURE.md` is not a published contract until a deterministic manifest schema,
  generated artifacts, and source-owned examples are added.
- The expression AST/runtime is authored here. The old `vera_spec` namespace is compatibility
  only. Keep the runtime Pydantic plus standard-library-only for the LEAN vendor copy.
- LEAN's `vera_spec/` directory is generated by `tools/sync_lean_vendor.py`; never edit it by hand.

## Build and validation

From the FinanceProjects workspace root:

```bash
python sigmarail-spec/tools/build.py --workspace .
python sigmarail-spec/tools/build.py --workspace . --check
python -m pytest sigmarail-spec/tests/ -q
python sigmarail-spec/tools/sync_lean_vendor.py --destination LeanProjects/VeraTradingLab/vera_spec
```

`--check` is read-only. It verifies pinned inputs and fails if regenerated artifacts differ. The
build must never connect to ClickHouse, load provider data, or populate a database.
